抽樣方法是先用來源影片影格辨識可見音符，再回填程式欄位；沒有用畫面上的 `MISS`、`PERFECT` 或 `GREAT` 疊字直接匹配 UID。完整逐案表與影格索引：

- `output/run_20261101T144725_489162Z/v711_work_order_0f/physical_note_links.csv`

### 灰色反例

在 `source_frame=397` / `video_frame=364` 可看到灰色長條，`candidate_id=397:candidate:11` 連到 `simple:1000007`，keys `J|K`。後續 `simple:1000020` 在 source 405–416 以較低 y 位置出現並完成排程／送鍵時間線。這足以否定「灰色完全未被偵測」的全域說法，但不能推導其他灰色音符皆無漏按，也不能把兩個 UID 當成 duplicate ground truth。

## B. 診斷負擔與處理落後

`src/live.py` 在每個已處理影格都呼叫 `draw_live_overlay(work, tracks, info, engine, dropped)`；即使 `recorder is None` 也會先繪製，只有後面才決定是否把影像交給 encoder。這是可疑的 CPU 路徑，但目前 run 的 latency 量測明確止於 decision stage，沒有 overlay/encoder 的逐階段耗時，因此不能從現有 CSV 證明它造成 2329 個 dropped frames。

本輪沒有第二個相同歌曲、相同畫面條件的 minimal-tracing 對照 run，也沒有可以把「全 tracing + 錄影」、「停用 tracing」、「停用錄影／overlay」分開歸因的資料。因此：

- 不宣稱 overlay 是掉幀根因。
- 不新增多執行緒、第二條 pipeline 或跳幀。
- 不修改 `draw_live_overlay` 路徑，等待受控 A/B。
- 目前唯一可證據支持的效能問題是 capture 64.14 FPS、processing 40.34 FPS 及 36.5% 未處理影格；具體瓶頸仍 UNKNOWN。

## C. PF gate 決策

624 筆 shadow row 全部是 Legacy `particle_posterior_too_wide`，width 約 40.04–79.30 ms。由於 118/172 UID 後續仍有 key-down，這些列不能當成 172 個救回機會；54 個未送鍵也沒有獨立實體真值。維持 `STOP_PF_GATE`，不把 40 ms 放寬到 80 ms，也不啟用 Active fallback。
